Deployment · 部署流程

一键部署为主，
少数 SDK 补齐。

绝大部分基础设施由 CDK 一次部署完成。少数资源因为 CloudFormation 尚未覆盖（多为 preview 能力），改用 SDK / AwsCustomResource 或控制台一次性配置。下面如实列出边界——这也是迁移时最容易踩坑的地方。

本演示有三种技术实现、两套部署轨道：方案 A（Connect）走主栈（Connect / Lex / Wisdom / AgentCore）；方案 B（Transcribe）与方案 C（Nova Sonic）走同一个独立 StreamingStack（-c enableStreaming=true），与 Connect 栈完全隔离。用下方选择器切换查看每种实现的部署与调优；两套轨道的对比表始终可见。

Flow · 部署步骤（方案 A · Connect）
前置：目标账号/区域启用 Connect Customer（下一代实例，agentic voice / AI agent designer 的前提，仅控制台）；Bedrock 控制台开通所需模型访问。
首次部署（AgentCore Gateway = NONE）：npm run deploy -- -c enableAiAgent=true。建好工具 / AgentCore Gateway（即 MCP 网关，注意与下方的 voice gateway 不是一回事）/ MCP 注册 / Lex / Flow / AI agent 全链路，输出 Gateway ID。
切 JWT（第二轮）：-c jwtDiscoveryUrl=…/.well-known/openid-configuration -c jwtAudience=<gateway id>。AgentCore Gateway 的 AuthorizerType 不可原地改，CDK 会整套替换为 CUSTOM_JWT。
（可选）开第二条线：追加 -c enableGateway=true。额外拉起 voice gateway（API Gateway WebSocket + Lambda）、EC2 设备主机（常驻 device.js，经 SSM 管理免 SSH）、IoT Thing、两张 DynamoDB 表。默认不带此开关，零新增资源。
SDK / 控制台补齐：AI agent ↔ security profile 关联、设为默认 self-service、工具挂载（见下表）。多数已封装进 AwsCustomResource 随 CDK 执行。

⚠️ 术语消歧：本页两个“网关”。AgentCore Gateway = 把工具以 MCP 暴露给 AI agent 的托管网关（带 CUSTOM_JWT）；voice gateway = 第二条线里设备接入的 API Gateway WebSocket + Lambda。两者独立，勿混。

Streaming · 方案 B/C 部署（Transcribe / Nova Sonic 共用）

自控流式管线怎么部署

方案 B 不依赖 Connect Customer / Lex / Wisdom，是一套独立的 ECS Fargate（ARM64/Graviton）+ ALB(WSS) 流式后端，与 Connect 主栈隔离，用 -c enableStreaming=true 单独开启。镜像用 podman 构建（本环境 Docker Desktop 被 org 登录门槛挡住）。

前置：无需 Connect Customer。仅需在 Bedrock 控制台开通模型访问——Claude Haiku（Transcribe 管线的 LLM）与 Nova 2 Sonic（端到端）。已有自定义域名/托管区则自动配 ACM + Route53。
一键部署：CDK_DOCKER=podman npx cdk deploy ConnectVoiceDemoStreamingStack -c enableStreaming=true。CDK 用 podman 构建两个 ARM64 镜像并推 ECR，建 VPC（公网子网、无 NAT）、ECS 集群、ALB(HTTPS/WSS)、DynamoDB turn-timings。
两个 Fargate 服务，一个 ALB：服务① Transcribe 管线挂 /ws/session；服务② Nova Sonic 挂 /ws/nova，由 ALB 按路径路由。两者必须分开——见下方「awscrt 版本冲突」。各带 /health 健康检查 + 会话粘滞（保持 WS 落在同一 task）。
前端接线：web/app.js 的 STREAM_WS 把每个方案映射到各自路径（transcribe→/ws/session、nova-sonic→/ws/nova）。改完 aws s3 sync web/ + CloudFront 失效即可，无需动 Connect 栈。

精确的每回合时间戳（ASR/LLM/TTS/E2E）由服务端写入 DynamoDB turn-timings，并经 WS 实时推给延迟面板——这正是方案 B/C 相对 Connect 黑盒最大的价值：可测量。

Streaming Tuning · 方案 B/C 调优与踩坑

把流式管线做稳、做快的那些细节

逐一实机验证：从会拆句、有回声、卡顿，到稳定的 ≈2.3s / ≈1.4s。

⏱️ 计时锚点 = 说完话

三段/端到端都从 t_speech_end（最后一帧语音）起算，而非说话起点。否则说得越久 ASR/总延迟越虚高，无法公平对比模型。

🎯 webrtcvad 判定「说完话」

用真·语音活动检测（voiced/unvoiced）而非能量阈值。能量 VAD 会把轻声词（如没重读的 “Tokyo”）当静音而误触发结束、拆句。

🧩 双条件结束回合

音频静音 ≥ VAD_SILENCE_MS 且 Transcribe 停更 ≥ SETTLE_MS 才结束。只看其一：会被 partial 突发拆句，或抢到滞后半句。SETTLE_MS=500 是地板——400 会截断最后一个词（Seattle→“Seat”）。

🔇 客户端半双工静音

回声抑制放在浏览器、按墙钟在播放期间静音麦克风。最初放服务端会过度静音、削掉用户下一句的开头。

📦 批量 512 样本再上行

AudioWorklet 每帧就发（≈344 次/秒）会压垮主线程导致丢帧；批到 ≈32ms 再经 WS 发。丢帧表现为识别断续、回合错乱。

🔧 一轮多工具

Bedrock Converse 一个回合可能有多个 toolUse 块（按 contentBlockIndex 区分）。“巴黎天气 + 纽约时间”会同时触发两个工具——按块分别累积 JSON，别拼接。

⚔️ awscrt 版本冲突 → 拆两服务

amazon-transcribe 需 awscrt~=0.26，aws-sdk-bedrock-runtime（Nova）需 awscrt~=0.32，无法共存于一个进程。故拆成两镜像、两 Fargate 服务，挂同一 ALB 用路径区分。

🧾 Nova promptStart 的 schema 要字符串

Nova Sonic 的 promptStart.toolConfiguration 里 inputSchema.json 必须是 JSON 字符串（Bedrock Converse 用 dict）。传 dict 会被拒：“Unable to parse input chunk”。

🔁 Nova 按 USER 转写分回合

Nova 每个响应流很多音频块，别每块开新回合；以新的 USER 转写为回合起点。否则时间戳被拆成一堆假回合。

🧱 镜像用 podman，架构对齐 ARM64

用 CDK_DOCKER=podman 构建（Docker Desktop 被 org 登录挡住）；镜像与 Fargate runtimePlatform 都设 ARM64。x86 镜像跑在 ARM64 task 会 exec format error；ARM 原生构建也免 QEMU 跨构建、Graviton 更省。

Tuning · 调优与踩坑细节（方案 A · Connect）

让它“像样”的那些细节

从能跑通到好用，逐一实机验证出来的经验。

🎬 单一开场白 + 连接中状态

Set voice 用 Matthew 播开场白，避免浏览器 TTS 造成“女声开场、男声回答”的割裂。代价：首次约 3–4 秒冷启动 —— 用一个脉冲式「⏳ 连接中」状态盖住，直到首次听到 Matthew 才切换。

💭 音量推断的状态机

用 Chime 的 realtime volume indicator（而非对 Chime 占用的 audio 元素做 Web Audio 分析）判断听/想/答，带迟滞与衰减防抖。Connect 不向浏览器推事件，状态只能由音量推断。

📝 字幕两边都取自日志

不做浏览器本地识别——那样无法反映 Connect 真实听到的。改为轮询 /transcript，从 AI agent 日志取 CUSTOMER/BOT 文本。用 FilterLogEvents（近实时、非索引查询），比 Logs Insights 快；延迟主要来自 Connect 的日志投递。

🔑 Q 会话必须显式创建

Flow 里在 Get customer input 前加 CreateWisdomSession，并把 session-arn 经 LexSessionAttributes 传给 x-amz-lex:q-in-connect:session-arn。否则 Lex 报“needs active session for Q In Connect”。

🧱 Lex locale 要可 build

只有 FallbackIntent 的 locale 无法构建；加一个带 utterance 的自定义 intent 才能 build，alias 指向已 build 的编号 version（不能指向 DRAFT）。alias 还需显式启用 en_US locale，否则运行时报未启用。

🔐 JWT 授权的两条硬约束

Gateway 的 AuthorizerType 创建后不可改，且 MCP application 的 URL 绑定 Gateway 无法迁移——切 JWT 时整链替换。allowedAudience = Gateway ID。自定义 Lex 角色还需补 wisdom:CreateSession/GetAssistant/SendMessage/GetNextMessage。

🗣️ 选组件化 agentic voice

bot 的 speech 选 Amazon Connect agentic voice，而非 Connect 里也提供的 voice-to-voice（Nova Sonic S2S）选项。本方案刻意用组件化的语音+编排，而非单一 voice-to-voice 模型。

🛡️ 只走 CloudFront 的合规入口

最初的 Lambda Function URL 被账号安全策略自动封堵；改为 CloudFront → S3(OAC) 静态站 + API Gateway，无任何公开 Function URL。S3 开启 Block Public Access，仅经 OAC 访问。第二条线的 voice gateway WebSocket 端点面向设备（非浏览器公网页面），由票据鉴权把关。

📟 设备端要 Node 22（全局 WebSocket）

device 进程用 Node 22 内置的全局 fetch/WebSocket，零依赖。但 AL2023 默认装的是 Node 18（无全局 WebSocket），UserData 必须先移除再从 NodeSource 装 22。否则设备日志一直报 WebSocket is not defined、拿到票却连不上网关。

🔌 $connect 不能 postToConnection

API Gateway WebSocket 在 $connect 阶段那条连接尚未就绪，无法向它推消息。观测页连上后要主动发一条 hello（在 $default 里回），才能拿到设备在线状态与会话信息。否则「加入音频」一直是暗的——推送全部静默丢失。

🎫 票据即鉴权，媒体不裸奔

设备→网关用 IoT Core 短期票（网关本地验，0 回调）；StartWebRTCContact 只有网关 IAM 能调、且仅验票后调；网页→Connect 的媒体靠一次性 ParticipantToken。join info 只定向推给配对 observer，不广播——攻击者拿不到就建不了媒体流。

🔔 设备待命，由观众唤醒

设备连上网关后不自动起会话，而是等观测页发 wake 才发起——贴近真实设备“被触发/唤醒词唤醒”才工作，也避免无人观看时空烧 Connect 费用。配合 SESSION 缓存（短 TTL）给迟到的观测页补发当前会话。
