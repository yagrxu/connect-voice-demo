Architecture · 系统架构

整体架构总览

同一套语音 AI 后端，两条接入线：①浏览器直连线——人对着网页说话，经 CloudFront（唯一公网入口，S3 用 OAC 保护、API 走 API Gateway）；②IoT 设备接入线——设备向 IoT Core 拿短期票，经 voice gateway（API Gateway WebSocket + Lambda）验票后接入。两条线共用同一个 Amazon Connect：语音与 AI 全部托管，工具以 MCP 暴露。

Pipelines · 三种技术实现对比

同一个演示页，三种可切换、可对比的技术实现

演示页顶部的「方案」下拉可切换三种实现，共用同一套前端与延迟面板做横向对比。方案 A（Connect）是托管组件化路线；方案 B（Transcribe）是自控三段流式（可精确计时）；方案 C（Nova Sonic）是端到端语音（最低延迟）。此对比表始终可见，下方按方案切换看各自的架构与数据流。

方案 B / C · 自控流式架构（共用基础设施）

前端 → 中间 → 后端：自控管线怎么搭

方案 B（Transcribe）与方案 C（Nova Sonic）不经 Connect，共用同一套流式基础设施：前端浏览器用 AudioWorklet 采集 16k PCM、经 WebSocket 上行；中间静态站走 CloudFront/S3，实时流走 ALB（WSS，按路径路由 /ws/session → B、/ws/nova → C）；后端是两个 ECS Fargate 服务（Graviton/ARM64），分别调用 AWS 托管 AI 服务，并把每回合时间戳写入 DynamoDB 供延迟面板读取。下图同时画出 B 与 C 两条后端，切换上方「方案」标签会高亮当前所选管线、淡出另一条（当前所选：方案 B / C 各自的 Fargate 服务与其调用的 AWS 服务）。

青色＝音频流；橙色＝文字；灰色虚线＝时间戳写库。 两个 Fargate 服务必须分开：Transcribe 依赖 awscrt~=0.26，而 Nova Sonic 的 aws-sdk-bedrock-runtime 需要 awscrt~=0.32——版本冲突无法共存于一个进程，故拆成两镜像、两服务，挂同一 ALB 用路径区分。三条管线的延迟都从「说完话」起算，因此面板数字可直接横向对比。

📟 IoT 设备接入（方案 B / C）

与方案 A 不同：这里传输就是一条 WebSocket，设备可带票直连 /ws/session 或 /ws/nova、双向推 PCM——无需信令/媒体分离，也不需要观测网页，比方案 A 的 voice gateway（WebRTC 所迫的复杂结构）简单得多。本演示以文档说明该路径，未单独实现；主演示页的「浏览器麦克风 → WSS → Fargate」已等价演示了 B/C 设备的数据路径，差别仅在 WSS 上加一层票据鉴权。方案 A 的完整设备接入见 IoT 设备接入演示。

Scenario Data Flow · 场景数据流（方案 B · Transcribe）

Transcribe 管线：一次提问怎么走（自控三段）

同样以「西雅图天气怎么样？」为例。与 Connect 不同：不经 Connect / Lex，浏览器直接用 WebSocket 连到 Fargate，服务端亲自串起 ASR → LLM → TTS 三段，因此每段都能精确计时。

1
浏览器 · 选 Transcribe，点击「开始通话」

建立 WSS 到 ALB → /ws/session，发送 start(language)。AudioWorklet 采集麦克风降采样到 16k PCM，批量 512 样本（≈32ms）经 WebSocket 上行。UI 显示「⏳ 连接中」。

2
Fargate 服务① · Transcribe 管线 · 开流

收到 start 后打开 Amazon Transcribe 流式会话，回 audio_format(16k) 与 status=active。UI 切到「🎙️ 正在听」。

3
你 · 说出问题

“What's the weather in Seattle?” 浏览器持续上行 PCM；服务端 webrtcvad 逐 20ms 帧判定是否为语音，Transcribe 同时回流式 partial / final 文字。

4
Fargate · 端点检测 · 判定「说完话」

当音频静音 ≥ VAD_SILENCE_MS 且 Transcribe 停止更新 ≥ SETTLE_MS，判定回合结束——锚定 t_speech_end（最后一帧语音），取最终整句。UI 切到「💭 思考中」。双条件避免把说话中的停顿误判成结束、也避免抢到滞后半句。

5
Fargate → Bedrock · LLM 推理 + 工具调用

Bedrock Converse 流式（Claude Haiku，可换模型）。命中 get_weather → 执行工具逻辑（tools.dispatch，确定性），把结果回喂模型产出一句回复。记录 t_llm_first_token / t_llm_done。支持一轮多工具（如「巴黎天气 + 纽约时间」）。

6
Fargate → Polly · 合成并回放

Amazon Polly neural（Matthew / Zhiyu）流式 PCM：首字节即 t_tts_first_byte / t_first_audio_out，边合成边经 WSS 下行。浏览器播放，并按墙钟半双工静音麦克风防回声。UI 切到「🔊 正在回答」。

7
Fargate · 计时落库 + 推面板 · 精确三段

turn.persist() 写 DynamoDB turn-timings；同时 WS 推 timing（asr / llm / tts / e2e，均从「说完话」起算）。面板即时显示分段条与总延迟（≈2.3s，LLM 主导）。

8
字幕 · 实时 · 随回合推送

transcript 消息（CUSTOMER / BOT）随回合直接经 WS 推送——无需轮询日志（与 Connect 的 CloudWatch 轮询不同），字幕与语音基本同步。

Scenario Data Flow · 场景数据流（方案 C · Nova Sonic）

Nova Sonic 管线：一次提问怎么走（端到端 S2S）

Nova Sonic 是一条双向 Bedrock 流：音频进、音频出，识别 / 推理 / 合成都在模型内部完成。因此无法切分单段，只报端到端总延迟——但最快（≈1.4s）。前端与 Transcribe 完全一致，只是连到 /ws/nova。

1
浏览器 · 选 Nova Sonic，点击「开始通话」

建立 WSS 到 ALB → /ws/nova，发送 start(language)。前端采集/上行 16k PCM 与 Transcribe 管线相同（同一 stream.js）。UI「⏳ 连接中」。

2
Fargate 服务② · Nova Sonic · 开双向流

打开 Bedrock InvokeModelWithBidirectionalStream（Nova 2 Sonic），下发 promptStart：system prompt + 工具配置（注意 inputSchema.json 须为 JSON 字符串，否则被拒）。回 audio_format(24k) + status=active。UI「🎙️ 正在听」。

3
你 · 说出问题

PCM 直接灌给 Nova；Nova 自己做 ASR 与端点/回合判定（无需 webrtcvad）。服务端收到 USER 转写即视为回合起点，锚定 t_asr_final（≈说完话，故不含说话时长）。

4
Amazon Bedrock · Nova 2 Sonic · 端到端生成

模型内部一体完成 识别 → 推理 → 语音合成。若需数据，发 toolUse 事件 → 服务端 dispatch 执行 get_weather → 结果回喂；随后流式吐出 24k PCM 音频 + ASSISTANT 转写。

5
Fargate · 首音频回放 + 计时 · 端到端总延迟

收到该回合第一个音频块即 t_first_audio_out，算 e2e = 首音频 − USER 转写；WS 推 timing(e2e) 并下行音频。浏览器播放、半双工静音。UI「🔊 正在回答」。面板显示端到端总延迟（≈1.4s），不可切分单段。

6
Fargate · 落库 + 字幕 · 按回合分段

turn.persist() 写 DynamoDB（e2e 而非三段）；每个 USER 转写开启新回合，避免把一次回复的多个音频块拆成多回合。字幕随 transcript 实时推送。

Voice Pipeline · 语音数据形态流转（方案 A · Connect）

音频 ↔ 文字：谁做 ASR、谁做 TTS

关键澄清：ASR 和 TTS 都由 “Amazon Connect agentic voice” 这一个 provider 完成（同一个提供方，两个环节）。Lex V2 不是 ASR 引擎——它是对话/编排层（NLU），负责管理回合、把识别出的文字交给 QInConnect intent，并通过 x-amz-lex 会话属性控制 ASR 行为（结束回合判定、barge-in）。下图按数据形态把链路拆开：青色＝音频流，橙色＝文字。

一句话记法：耳朵和嘴（ASR / TTS）＝ agentic voice；思考与选工具＝ orchestrator AI agent；Lex V2 只是接线盒——Connect 的语音入口只能接一个 Lex bot，它用 QInConnect intent 把整句原样转发给 AI agent，并承载 ASR 的会话控制参数（x-amz-lex），自身不做 ASR、不做对话逻辑。音频只在浏览器 ↔ Connect 之间以 WebRTC 流动，进入 Connect 后立刻转成文字，AI 全程处理文字。

Scenario Data Flow · 场景数据流（方案 A · Connect）

一次语音提问，数据怎么走

以“西雅图天气怎么样？”为例，走 ①浏览器直连线，从点击开始到听见回答的完整链路。

②IoT 设备接入线只有入口第 1 步不同：不是浏览器直接调开放的 /webcall，而是设备带票连上 voice gateway、由网关验票后代为调用 StartWebRTCContact（/webcall 的开放触发被收口到网关）。从第 2 步起两条线完全一致——同一个 Contact Flow、同一套 AI agent 与工具。详见下方「第二条线」。

1
浏览器 · 点击「开始通话」

网页向 /webcall 发请求；后端 Lambda 调用 StartWebRTCContact，返回 Chime 会议/参会者信息。浏览器用 Amazon Chime SDK 建立 WebRTC 语音流。UI 显示「⏳ 连接中」。

2
Connect · Contact Flow · 建立会话并问候

Contact 进入 Flow：Set logging → Set voice（agentic voice, Matthew）→ CreateWisdomSession 建立 Q in Connect 会话 → Get customer input 交给 Lex bot，并把 session-arn 作为 Lex 会话属性传入。Matthew 播报开场白，UI 切到「🎙️ 正在听」。

3
你 · 说出问题

“What's the weather in Seattle?” — agentic voice 的流式 ASR 识别语音；用户停顿时结束回合。UI 切到「💭 思考中」。

4
AI agent · Orchestrator · 推理 + 选择工具

Lex 的 AMAZON.QInConnectIntent 把话交给 orchestrator AI agent。Claude 依据 orchestration prompt 判断需要天气数据，决定调用 get_weather 工具。

5
MCP · AgentCore Gateway · 工具调用

AI agent 经 AgentCore Gateway（CUSTOM_JWT 授权，audience = Gateway ID）以 MCP 协议调用工具；Gateway 路由到我们的工具 Lambda 执行 get_weather("Seattle")，返回确定性结果。

6
AI agent · 生成回答

拿到工具结果后，Claude 生成一句自然语言回复，用 <message> 包裹（orchestrator 要求）。

7
Connect · agentic voice · 合成并回放

回复文本经 agentic voice 合成为语音，通过 WebRTC 播回浏览器。UI 切到「🔊 正在回答」。

8
字幕 · 异步 · 从日志补齐双方文本

Connect 把 TRANSCRIPT_ORCHESTRATION_MESSAGE（含 CUSTOMER / BOT 文本）投递到 CloudWatch；网页每 1.5 秒轮询 /transcript（FilterLogEvents，非索引查询）把双方对话渲染成字幕，便于对比识别与回答。

Voice Gateway · 抽象出独立网关（方案 A · Connect）

第二条线：IoT 设备如何鉴权接入语音网关

直接对话线是「人对着浏览器说话」。而客户的真实场景是「设备连上一个语音网关」。我们把语音能力后面隐含的 voice gateway 抽象成独立组件：一个真实的 IoT 设备（EC2 常驻进程）向 IoT Core 拿短期票，用长连接接入网关；网关验票通过后才发起 Connect 会话。信令（鉴权+编排）由网关走 WebSocket，媒体（音频）由网页代表设备麦克风直连 Connect——两者分离，是 WebRTC 的标准做法。

设备 → 网关

网关验票（Mode A 本地验，0 次回调 IoT Core）。无票 / 票坏 → 拒连。

起会话

StartWebRTCContact 只有网关的 IAM 角色能调，且仅在验票通过后调——这堵上了原本开放的 /webcall。

媒体不裸奔

Connect 返回的 Meeting/Attendee 是一次性会话票，网关只定向推给配对的观测网页，攻击者拿不到就建不了媒体流。
